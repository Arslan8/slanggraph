# Response to the macOS campaign review

The parsing/refusal correction is implemented. The proposed CPU conclusion is not supported by the reproduced behavior on this Mac. The new matched-host run uses commit `79c6309604835277333393d426a0c7fc22eb49e0`; its measured outcomes and remaining limitations are in RESULTS.md.

## CPU mechanism and direct qualification

Linux installs per-process limits with `resource.setrlimit(resource.RLIMIT_CPU, (seconds, seconds))` in `_linux_worker.py::_apply_limits`; it rejects subsecond requests rather than rounding. The optional cgroup manager also configures memory/pids and `cpu.max = 100000 100000`. That CPU setting limits bandwidth, not cumulative CPU consumption across a process tree. An aggregate CPU-time requirement therefore cannot be credited on either current adapter.

The Mac native launcher already calls `setrlimit(RLIMIT_CPU, (limit, limit))`: `limit()` constructs equal soft/hard limits at line 113; `worker()` invokes it at line 131, before `sandbox_init()` at line 134 and Python's `dlopen()` at line 142. These calls are present at revision `33504f3` too. There was no missing installation to add.

`cpu-sanity/transcripts.json` contains all 30 direct Mac observations, including full command lines, the deny-default Seatbelt profile, initial soft/hard limits and SIGXCPU handler, exit status, stdout/stderr and parent-observed user/system CPU. Five repetitions of each condition show:

| Body | Seatbelt only | RLIMIT_CPU (1,1) only | Seatbelt + RLIMIT_CPU (1,1) |
| --- | --- | --- | --- |
| Computation-heavy | Completes 2 CPU seconds | SIGXCPU at about 1 CPU second | SIGXCPU at about 1 CPU second |
| Syscall-heavy process-time loop | Completes 2 CPU seconds | Completes 2 CPU seconds | Completes 2 CPU seconds |

The limited syscall-heavy runs consumed approximately 2.016–2.023 CPU seconds as independently observed by the parent. The overrun reproduces without Seatbelt. This establishes a qualification failure for the promised total-CPU ceiling on the tested macOS 26.7.2 build; it does not establish that every macOS build has the same behavior. We retain the native guard but refuse a mandatory total-CPU requirement. Calling that requirement enforced would contradict these transcripts.
